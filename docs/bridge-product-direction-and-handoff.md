# 飞书与微信 Bridge：方向与当前进展

更新日期：2026-09-20

## 想做的事情

希望把飞书 Bridge 和微信 Bridge 做成同事可以方便使用的 AI 助手入口：同事直接在聊天工具中提需求，Bridge 负责调用本地或容器中的 Agent 完成搜索、分析、文件处理和内容生成。

这个方案需要同时满足两个目标：

1. **好用**：接入简单，能够连续对话，支持公开网页搜索，并能生成和回传常见文件。
2. **有边界**：不同用户的会话、文件和运行状态相互隔离；Agent 可以充分操作自己的空间，但不能读取宿主机个人数据、其他用户数据或 Bridge 密钥。

期望的基本结构是：

```text
飞书 / 微信用户
        |
        v
Bridge（鉴权、会话路由、文件回传、审计）
        |
        v
用户独立工作区 + Docker 容器
        |
        v
Codex / 其他 Agent
```

## 当前已经做的工作

### 飞书 Bridge

当前仓库为 `feishu-bridge`。飞书链路已经基本跑通，现有能力包括：

- 飞书消息接收、回复和连续会话。
- 根据会话选择独立工作区。
- 使用 Docker 容器运行 Codex。
- 容器内工作目录为 `/workspace`。
- 容器内 Codex 可以执行命令并在自己的空间写文件。
- 生成的文件可以通过飞书回传。
- 支持公开网页搜索及网页正文的只读抓取。
- 已处理 Docker 内二次 sandbox 导致的 `bwrap` 报错。
- 已处理宿主机旧 thread 在容器内无法恢复的问题。
- 已处理容器 CA 证书和 Codex 配置缺失问题。

真实飞书链路已验证：

- 可以在工作区创建并回传 `container-test.txt`、`security-test.txt` 和 `private-a.txt`。
- 所有近期测试请求均通过 `container: true` 的容器流程运行。
- 容器中没有暴露 `LARK_CHANNEL` 等 Bridge 环境变量，这是预期的隔离行为。
- 在容器 `/tmp` 中创建文件或目录不会写入宿主机 `/tmp`。
- 宿主机个人目录、Chrome 数据及路径穿越测试未发现文件被读取或回传的证据。

### 微信 Bridge

总体方向与飞书一致：让同事通过微信使用 Agent，同时具备独立空间和权限边界。

目前这份记录没有对微信 Bridge 做同等级别的代码、容器和真实消息链路审计。因此不能直接认为飞书已有的隔离能力已经自动覆盖微信。后续需要把两者的公共能力下沉为一致的运行层，或者为微信单独完成同一套验证。

## 当前权限限制是如何实现的

权限限制不是依靠模型说“我不能访问”，主要依靠 Docker 文件系统隔离。

容器目前只获得必要挂载：

- 用户或会话工作区挂载到 `/workspace`。
- 工作区自己的 Codex 状态挂载到 `/codex-home`。
- Codex 初始化配置通过只读 `/seed` 提供。

未挂载的宿主机目录不会出现在容器的文件系统中。因此，即使 Codex 在容器内使用接近全权限模式，也只能完整控制容器和被显式挂载的目录。

当 Agent 回复“没有权限”时，需要区分：

- Docker 或操作系统确实返回了路径不存在、权限不足或连接失败。
- Agent 根据提示主动拒绝，但底层并没有硬限制。

安全结论必须以实际挂载、网络策略、命令结果和审计日志为准，不能只依据模型回复。

## 尚未解决或未充分验证的事项

### 1. 跨用户隔离

当前已经验证单个飞书私聊可以拥有自己的工作区，但还需要两个真实用户完成测试：

1. 用户 A 创建仅自己可见的文件。
2. 用户 B 尝试读取该文件。
3. 在宿主机检查两人的工作区和 Codex 状态是否确实分离。

私聊通常可以按独立 chat scope 隔离；普通群聊是共享 chat scope，不能默认理解为群内每个人都有独立空间。群聊是否按用户拆分需要单独设计。

### 2. 容器网络边界

当前容器使用 Docker `bridge` 网络，可以访问互联网，但尚不能保证完全无法访问宿主机网络服务，例如 `host.docker.internal`。

后续应考虑：

- 禁止访问宿主机网关、内网地址和云元数据地址。
- 公开网页访问统一经过受控的只读代理或 Bridge 抓取服务。
- 对 DNS、目标 IP、重定向和响应体大小做限制。
- 记录必要的网络审计信息，但不记录凭据和隐私正文。

### 3. Codex 凭据保护

目前 `/seed` 以只读方式向容器提供 Codex 认证和配置。只读可以防止修改，但不能防止容器内进程读取并通过网络外传。

后续需要评估：

- 使用短期、低权限、可轮换的凭据。
- 不把长期宿主机凭据直接挂入用户容器。
- 通过宿主机代理完成模型请求，让用户容器不接触真实凭据。
- 对每个用户或运行分配独立配额、速率限制和审计标识。

### 4. 容器资源限制

还需要补充 CPU、内存、进程数、运行时长和磁盘空间限制，防止单个请求占满宿主机资源。

建议至少增加：

- CPU 和内存上限。
- PID 数量限制。
- 单次任务超时。
- 工作区容量或配额。
- 容器只读根文件系统，并单独提供必要的可写目录。
- 删除不必要的 Linux capabilities，启用 `no-new-privileges`。

### 5. 审计和结果可信度

目前日志能够确认请求是否进入容器、任务是否正常结束、是否回传文件，但不会完整保留每条命令及回复正文。因此“任务正常完成”不等于“越权测试已经证明安全”。

后续需要增加经过脱敏的安全审计事件，例如：

- 容器启动参数摘要。
- 实际挂载列表摘要。
- 工作区标识和用户/会话映射。
- 被阻止的路径和网络目标分类。
- 文件创建、读取和回传事件。
- 安全测试结果及对应证据。

## 推荐的下一步

按优先级继续：

1. 用第二个真实飞书用户完成跨用户文件隔离测试。
2. 测试并封锁 `host.docker.internal`、宿主机网关和内网网段。
3. 改造 Codex 凭据传递方式，避免用户容器直接读取长期凭据。
4. 增加 Docker CPU、内存、PID、磁盘和运行时限制。
5. 明确群聊的隔离语义：按群共享，还是按群内用户拆分。
6. 给微信 Bridge 接入相同的容器运行层，并重复真实消息链路测试。
7. 建立自动化安全回归测试，避免后续功能修改破坏隔离边界。

## 当前判断

飞书 Bridge 已经达到“可以继续试用和迭代”的状态：消息链路、Docker 运行、工作区写入、文件回传和公开搜索基本可用。

但它目前更适合受控范围内试用，还不能称为已经完成的多租户安全平台。正式开放给更多同事之前，至少应完成跨用户隔离、宿主机网络封锁、凭据保护和资源限制。

长期目标不是让 Agent 什么都不能做，而是让它在自己的个人空间里尽量自由，同时把宿主机、其他用户和平台密钥放在明确且可验证的边界之外。
